# Spec: mascot-wardrobe public release

Status: approved by the maintainer's brief. Scope: this repository only. Nothing in this
spec publishes, pushes or installs anything.

## 1. Goal

Turn the existing prototype into a generic, public-ready Python application named
**mascot-wardrobe**. A user supplies a PNG of their own mascot and a body box. The tool
generates six outfit variants **once** with local Pillow overlays, then picks one of
the existing variants by temperature as often as needed. There is no AI/LLM
dependency, no recurring inference and no semantic image understanding.

## 2. Pre-approved decisions

- License: MIT for code and for the bundled original artwork.
- Channels are export-only (files). No real account changes are implemented or claimed.
- Body box is configurable. The compositor is generic, geometric and not semantic.
- Country presets (BR, GB, US, JP) are documented product presets, not universal truth.
- Python >= 3.11. Distribution and import name: `mascot-wardrobe` / `mascot_wardrobe`
  (the old `-ddd` distribution suffix is removed).
- A 6-hour scheduler (cron or systemd user timer) is an **example only**; nothing is installed.
- Non-production only. No GitHub remote is created or pushed to.

## 3. Requirements and acceptance criteria

Each criterion (AC) must be traceable to at least one automated test or one recorded
verification command (see section 6).

### 3.1 Domain and behavior

- AC-1 Six categories `very_cold, cold, mild, ambient, warm, very_hot`; `mild` is the intentional sixth.
- AC-2 Each profile has five strictly increasing Celsius boundaries; a boundary value belongs to the upper category.
- AC-3 Profiles BR, GB, US, JP exist, are configurable via a custom profiles JSON, and unknown countries fail with a helpful error.
- AC-4 Fahrenheit input converts deterministically to Celsius; values outside -90..65 C are rejected; NaN/inf/bool are rejected.
- AC-5 Selection reads the manifest only: it never regenerates images and never calls a model or network.
- AC-6 Category labels and user-facing text are English.

### 3.2 Weather (Open-Meteo)

- AC-7 Weather is optional (`--live-weather`) with explicit latitude/longitude; no geolocation.
- AC-8 Units are explicit Celsius; the response unit is verified.
- AC-9 Timezone semantics: the request uses GMT; naive timestamps use the response `utc_offset_seconds`; all comparisons are in UTC.
- AC-10 Stale (older than 3 h) or future (more than 15 min ahead) readings are rejected, never replaced with invented values.
- AC-11 Network, HTTP, JSON and size failures surface as bounded, helpful errors (exit code 2); tests use a deterministic fake transport.

### 3.3 Architecture and safety

- AC-12 Layers are `domain` (pure), `application` (use cases and ports), `wardrobe`/`channels`/`infrastructure` (adapters), `interfaces` (CLI). ADRs describe the code as it is. Public imports keep working.
- AC-13 No hardcoded personal paths, usernames, IPs or production directories in tracked files. Application write roots are explicit and configurable rather than tied to a machine path.
- AC-14 Output paths reject traversal and symlinks; file names and slugs are validated; input PNG size is bounded.
- AC-15 No runtime model API calls, no credentials required for file exports.

### 3.4 Channels

- AC-16 `whatsapp`, `telegram`, `discord`, `hermes-cli` exports copy bytes into `<export-dir>/<channel>/<slug>/`, are idempotent (second run reports `unchanged`, mtimes and hashes unchanged), and report `remote_sync: false`.
- AC-17 Docs distinguish sandbox/file export from REAL account changes. Changing a Telegram bot's own avatar is not implemented by this project and never claimed (do not assert the Bot API cannot do it; the project is export-only).
- AC-18 The sandbox HTTP bridge, if retained, binds loopback only, uses a neutral header name (no personal mascot name) and is described as a local contract test, not a real WhatsApp integration.

### 3.5 Artwork

- AC-19 An original friendly rounded cream/mint/coral creature exists as editable SVG source, a transparent example PNG, a wide hero banner and a six-outfit contact sheet, all generated by a reproducible script in the repo, with authorship and MIT license stated.
- AC-20 The example PNG produces six visually distinct outfits (six distinct pixel hashes) and pixels above the body box (head) are byte-identical to the source.

### 3.6 Documentation and project hygiene

- AC-21 README embeds the hero, explains generate-once/select-often, gives clean-venv install and quickstart, the weather command, an offline deterministic demo, limitations and security.
- AC-22 CONTRIBUTING.md, SECURITY.md, CHANGELOG.md, LICENSE (MIT) exist. Stale personal evidence (`docs/wardrobe-tests.txt`) and private-specific notes are removed or translated and sanitized.
- AC-23 Docs cover all country boundaries, C/F behavior, timezone, Open-Meteo dependency, failure and stale behavior, and a scheduler example (cron and systemd user timer) that is explicitly not installed.
- AC-24 CI workflow runs tests, ruff, build and a secret scan, with pinned action versions verified from authoritative sources.
- AC-25 A secret scanner (detect-secrets) is run before every commit; a sanitized report is kept outside the repo and a concise verification doc is tracked.

### 3.7 Verification

- AC-26 Strict TDD for new or changed behavior with RED/GREEN logs saved outside the repo.
- AC-27 Full test suite green, `ruff check` and `ruff format --check` clean, wheel and sdist build, a fresh venv wheel install runs CLI help and a real offline generate -> select -> export -> repeat flow.
- AC-28 Determinism: repeated generation yields identical output hashes.

## 4. Baseline facts (recorded before editing)

- 34 tests; 9 fail only because the code hardcodes a machine-specific scratch root and a
  fallback project root. 25 pass.
- `ruff check` reports 35 findings and `ruff format --check` would reformat 10 files.
- Docs and several identifiers are in Portuguese and contain a personal mascot name in an
  HTTP header, hardcoded absolute paths, and an audit reference.

## 5. Non-goals

Semantic segmentation, generative image models, real WhatsApp/Telegram/Discord account
mutation, installing services, publishing to GitHub or PyPI.

## 6. Traceability

A table mapping each AC to tests, plans and ADRs lives in `docs/traceability.md` and is
completed during implementation.

## 7. Suggested step grouping (about three cohesive steps)

1. Foundation: git hygiene, rename, English translation, remove machine paths, fix baseline failures, lint/format, neutral bridge header, weather failure handling.
2. Artwork and tooling: art generator, SVG/PNG/hero/contact sheet, example end-to-end tests.
3. Docs, CI, scanner, packaging verification, ADRs, traceability, changelog.
